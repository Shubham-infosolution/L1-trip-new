Requested policy
For a pending primary MySQL trip (trip_status = 0), when no per-vehicle/per-trip
Redis geofence state is available, assume source-IN at lifting_date (tbl_trip.c_date).
A valid source-OUT GPS packet strictly AFTER that time starts the trip. The saved
trip_date and start coordinates come from the actual packet, not NOW(). Pending
trip_date is NULL and therefore is not the comparison cutoff.

The assumption is explicitly recorded as source_assumed_in_at; it is NOT a
fabricated GPS source-entry packet. source_entered_at remains real evidence or
NULL. trip_started logs and write intents include start_basis=MISSING_REDIS_STATE
and assumed_source_in_at. Actual observed departures use OBSERVED_SOURCE_EXIT.

Scope and boundaries
- Live and historical $PVT packets use the same GPS-time rule. Source geometry,
  GPS fix, packet validation and lifting-time checks still apply.
- No GPS: no start. Inside source: no start. At/before lifting: no start.
- An assumption initialized from a pre-lifting packet survives a worker restart
  until a qualifying post-lifting observation. Actual source-IN then OUT remains
  an observed departure.
- Existing OUTSIDE state without an observed exit is NOT missing state. Existing
  states and historical replay cursors cannot silently create this fallback.
- Started/completed trips cannot restart. Trips remain independent by vehicle+ID.
- End requires destination-IN GPS time strictly after saved trip_date. A first
  packet already at destination can start a missing-state pending trip, but a
  later destination packet is required to end it; one timestamp cannot do both.
- Only received/retained packets can supply timestamps. Late-arriving older
  evidence does not rewrite an already committed start/end timestamp.
- Redis write intent precedes MySQL UPDATE. A connection failure preserves queued
  work; lost-commit retries reconcile exact recorded targets without duplicate
  writes. Completed geofence keys are removed only after confirmed MySQL commit.
